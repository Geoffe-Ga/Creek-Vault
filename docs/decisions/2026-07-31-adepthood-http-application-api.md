## Framing

`/v1` is the Adepthood **application** adapter over HTTP/JSON. The existing
MCP surface, documented in
[`creek-tools/docs/mcp.md`](../../creek-tools/docs/mcp.md) and in the
[MCP contract ADR](./2026-06-30-adepthood-creek-mcp-contract.md), remains the
**agent** adapter. Both call one behavioral implementation —
`creek_mcp.tools.*` — through two different wire vocabularies. `/v1`'s own
vocabulary is
[`creek_mcp/api/models.py`](../../creek-tools/creek_mcp/api/models.py); its
published fixture bundle is generated by
[`creek_mcp/api/bundle.py`](../../creek-tools/creek_mcp/api/bundle.py) into
[`docs/contracts/adepthood-v1/`](../contracts/adepthood-v1/).

**Protocol choice is not a confidential-compute guarantee.** HTTP delivers no
encryption at rest, no attestation, and no key custody. TLS, where configured
per
[`_require_transport_confidentiality`](../../creek-tools/creek_mcp/server.py),
is transport confidentiality only — it protects bytes in flight and does
**not** satisfy an intimate-transit contract. Encrypted-at-rest / attested /
client-side-key hosting is owned entirely by
[#757](https://github.com/Geoffe-Ga/Creek-Vault/issues/757). No sub-issue of
epic #1071 (#1073–#1077) may stub an intimate success path or widen the
remote tier ceiling in order to demo a capability early — see
[What this ADR does NOT decide](#what-this-adr-does-not-decide).

## Versioning

`/v1` in the route path is the HTTP major. Below that, exactly one
`contract_version` — `creek_mcp.contract.CONTRACT_VERSION`, currently `0.4.0`
— covers both the MCP surface and `/v1`, because the epic's premise is one
behavioral implementation: a shape change in a shared `creek_mcp.tools.*`
function changes what both adapters can honestly promise at the same moment.
`ontology_version` (`aptitude-wavelength/2026-05-23`) is tracked separately —
it is the shared APTITUDE-frequency vocabulary, not the wire shape, and it
changes on its own cadence (see
[`2026-05-23-frequency-naming.md`](./2026-05-23-frequency-naming.md)).

**Compatibility rule.** Below contract `1.0`: exact-minor match —
`client_minor == server_minor`, patch ignored. At or after `1.0`: major must
be equal, and `client_minor <= server_minor` (an older client may still be
served by a newer, backward-compatible minor).

**#1072 deliberately does not bump `CONTRACT_VERSION`.** This ADR and the
models it describes change no wire behavior — they are the *first* published
shape of a surface that did not exist before, not a revision of one. Bumping
the constant for a from-scratch addition would hollow out the ADR↔code pin
test (`test_adr_publishes_the_runtime_contract_version`,
`test_adr_publishes_the_runtime_ontology_version` in
`tests/test_adepthood_contract_models.py`): the point of that test is that
the version string an Adepthood client reads off this document is the
version string the running server actually speaks. The bump is owed the
first time any of #1073–#1077 changes a wire shape.

**The bump arrived from the other adapter twice, and every earlier minor
stayed served.** Because one `CONTRACT_VERSION` covers both surfaces, an
MCP-only change moves the number a `/v1` client negotiates against. #1023 —
which adds the `creek.upload` MCP tool and touches no `/v1` shape — moved the
constant to `0.3.0`. #1246 — which gives `creek.purge.*` a third status,
`partial`, so an incomplete erasure stops reporting unqualified `ok`, and
likewise touches no `/v1` shape — moves it to `0.4.0`. Both times
`SUPPORTED_CONTRACT_MINORS` was **widened**, to `("0.4", "0.3", "0.2")`,
rather than shifted, so an existing client still sending
`X-Creek-Contract-Version: 0.2` is served exactly as before. This is the case
the constant was always shaped for: the compatibility window — not the number
— is what keeps a shared version string honest instead of breaking.

**Wire mechanism.** Every `/v1` **capability** endpoint requires an
`X-Creek-Contract-Version: <major.minor>` request header; a missing or
mismatched value is refused `409 incompatible_version` before any vault read.
`GET /v1/capabilities` requires nothing on this axis, deliberately — the
negotiation endpoint must never itself be able to fail to negotiate.

`GET /v1/health`, added by #1074, is exempt for a different reason: it is not
part of this published contract at all, so there is no contract version for it
to negotiate. Gating liveness on the header would leave a client on the wrong
version unable to tell "the server is down" from "the server is up and we
disagree about versions" — the two facts a probe exists to separate.

**An Adepthood client pinned to `0.1.0-draft` is a hard break, not a
negotiation.** It receives `409` on every journal/reflection/wheel call and a
`200` from `/v1/capabilities` carrying the server's real
`contract_version`/`contract_minor`/`supported_contract_minors`, so it can
render "upgrade required" instead of collapsing to "vault unavailable" — the
exact collapse this epic exists to stop happening at the application layer.

**Deprecation policy, stated honestly.** Every response model is
`extra="forbid"` (`_WireModel.model_config`), so *adding* a field to a
response is itself a minor bump, not a backward-compatible addition a client
can ignore. Below `1.0` there is no soft-deprecation window: the change-log
table at the bottom of this document is the notice, and the re-published,
re-hashed fixture bundle under `docs/contracts/adepthood-v1/` is the
migration artifact. There is no grace period to promise, so none is implied.

## Capabilities — the states a handshake can report

`GET /v1/capabilities` is always HTTP `200` when the server is reachable, the
caller is authenticated, and the request itself is well formed; the **readiness
state** lives entirely in the `status` field of `CapabilitiesResponse`, never in
the HTTP status line. No condition of the *server* — no vault, an unreadable
config, a contract minor this server cannot speak — can move it off `200`.

**The promise is about the server's state, not about accepting a malformed
request.** A caller that declares an inadmissible `X-Creek-Tier-Ceiling` gets
`422 invalid_request` here exactly as it does on every other route, because the
ceiling gate is one edge check above the router with **no per-route exemption**
(see [INTIMATE](#intimate)). That is deliberate, and it does not weaken
negotiation:

- The ceiling is the caller's own free, per-request choice, not something it is
  pinned to the way a compiled-in contract version is. Omitting the header
  always works and fails closed to `open`, so the caller is one trivially
  discoverable step from a `200` — which is precisely the situation the version
  exemption exists to rescue a client *from*, and why that axis needs an
  exemption and this one does not.
- The refusal is `invalid_request`, a distinct machine-readable code that a
  conforming client (which branches on `code`, never on prose) can tell apart
  from every server-side condition. It does not collapse into "vault
  unavailable" — the failure this epic exists to stop.
- `intimate` is not a constructible member of `WireTierCeiling`, so a client
  generated from the published bundle cannot send it. Reaching this refusal
  means leaving the published contract.
- Most importantly, **any** exemption makes the ceiling gate route-aware, and
  that is the property being protected. Its whole value is that it is one edge
  check with no per-path branch: what it does is a function of the declared
  header alone, so reviewing it does not require enumerating the route table,
  and #1075–#1077 cannot get it wrong by omission. The version gate can afford
  a per-route flag because it is not the thing standing between a network
  caller and intimate content; this gate is.

  Two exemption shapes were considered and both are refused. *Skip the check for
  this route* is the obviously dangerous one — copy-pasted onto a handler that
  really reads the vault, it reads it uncapped. *Degrade an inadmissible value
  to `open` for this route* is genuinely not dangerous in itself (`open` is the
  strictest ceiling, and is already what an absent header yields), so it is
  worth saying plainly that it is refused on different grounds: it would break
  the standing rule that an absent ceiling fails closed while a **bad** one is
  refused and never repaired. Coercion is how a typo'd or hostile value ends up
  admitted at *some* ceiling rather than at none, and a rule that holds
  everywhere except on one route is a rule a reader has to check rather than
  know.

The published OpenAPI document therefore lists `422` among `getCapabilities`'
responses, and that is correct rather than a generator artefact.

Both version strings are present in every one of the three bodied states.

**Row (c)'s `vault.available` used to read `—` here and in `docs/api.md`. That
was wrong, and the correction is #1150's.** `handle_capabilities` computes
`available` from the readiness probe unconditionally and `_render` emits
`VaultState(available=available)` at *every* status, so an `incompatible` body
always carries a concrete boolean; only `capabilities` is emptied for a
non-`ok` status. `—` reads as absent-or-unspecified and it is neither. #1148
changed the *audit* half alone — at an unserved minor the probe runs
`audited=False`, so a poll at a version this server cannot speak no longer
drives one locked, fsync'd append per request. Keeping the probe is deliberate,
and `creek_mcp/httpapi/capabilities.py`'s own docstring argues it: skipping it
would report `available: false` against a healthy vault and turn "you are on an
old contract" into "your vault is down". **Whether it should nonetheless be
reordered away at that status stays open** — recorded as open question 6 in the
[sibling ADR](./2026-06-30-adepthood-creek-mcp-contract.md#open-questions-resolve-before-accepted)
rather than on an issue, because #1150 asked for this table and #1148, which
owned the reordering, is closed. This table states what the code emits, and the
two documents' cells are now asserted identical to each other by
`tests/test_mcp_contract_adr_shipped_surface.py`.

The **unreachable** row is distinguished purely by transport outcome:
connection refused, a DNS/TLS failure, a timeout, a non-JSON body, or an HTTP
status outside the closed set the contract publishes — `{200, 401, 403, 404,
409, 415, 422, 500, 501, 503}` (`ALLOWED_HTTP_STATUSES` in the contract test
suite, derived from `ERROR_STATUS`'s range plus `200`; `415` joined it at
contract `0.8.0` with `unsupported_source`). A conforming client MUST map it to
a distinct local state and MUST NOT synthesize a capabilities body, and MUST
NOT fold it into "uninitialized" — those are different facts an operator
needs to act on differently.

**The advertised list is now caller-dependent (contract `0.8.0`).** It is the
intersection of what this server implements with what the caller's declared
contract minor published: `CAPABILITY_SINCE_MINOR` in `creek_mcp/api/models.py`
is the one table, and `POST /v1/uploads` refuses a caller below `0.8` with
`incompatible_version` off that same table, so what is withheld here is
unreachable there. A caller that declares no minor at all is shown the full
list — it has vendored nothing that a newer capability could contradict, and
every content route refuses an undeclared minor anyway.

**The build-out divergence is closed (#1112).** While epic #1071 was being
built, this section recorded a deliberate gap: the running server advertised
only what it had actually implemented — [#1074](https://github.com/Geoffe-Ga/Creek-Vault/issues/1074)
shipped `capabilities` alone and #1075–#1077 each added one — while the
committed `examples/capabilities/success.json` fixture already documented the
completed steady state, because re-publishing and re-hashing a consumer-pinned
artifact four times inside one epic would have trained that consumer to re-pin
without reading. **#1077 and epic #1071 are both closed**, so there is no gap
left: `IMPLEMENTED_CAPABILITIES` is `frozenset(Capability)`, the fixture lists
the same six, and a live response over a vault declaring the current minor
returns the same six. `tests/test_v1_api_capabilities.py` asserts those three
and the enum as **one four-way equality**, which is what replaced the old test
that existed to record the divergence.

The mechanism that made the gap safe is unchanged and still worth having. A
route that is mounted but unbuilt answers `501 unsupported_capability`, and
advertising it in the handshake would be exactly the "the contract says yes,
the call says no" divergence this epic exists to remove — a client would
negotiate a capability and then discover, one round trip later, that it does
not exist. `IMPLEMENTED_CAPABILITIES` is kept as a distinct constant rather
than folded away for that reason: it is what makes "a route exists but is
unbuilt" expressible at all, and it drives both the advertised list and which
routes answer `501`, so the two can never disagree.

**A fifth state the issue's Problem section did not name.** Post-#961,
`unclassified` ranks with `personal`, not `open`, on the MCP ceiling (see
[Tier ceiling semantics](./2026-06-30-adepthood-creek-mcp-contract.md#tier-ceiling-semantics)).
So an initialized vault whose fragments have been ingested but not yet
classified — every one of them explicitly tiered `unclassified` — returns an
all-zero `WheelResponse` at `ceiling=open`: `total_classified: 0`, every
`WheelFrequency.count` zero, every `share` `0.0`. That is byte-identical to
the response for a genuinely empty corpus. Distinguishing the two would hand
a caller a corpus-size oracle **below the admitting ceiling** — "your vault
has content I won't tell you about" is itself information about the vault —
so this ADR records the collapse as deliberate, not as an oversight to file.
**Client rule: an all-zero wheel means "nothing admitted at your declared
ceiling," never "you have no entries."** It must not be rendered as an empty
state. The operator remedy is `creek classify` (or `creek process`).

## Journal upsert

`PUT /v1/journal-entries/{external_id}`.

The path carries `external_id` — the idempotency key, which is what makes
this a `PUT` rather than a `POST`. The body carries
`{content, timestamp?, tier}` (`JournalUpsertRequest`); the ceiling arrives
on the `X-Creek-Tier-Ceiling` header (see [INTIMATE](#intimate)). The
response reuses `journal_ingest_tool`'s existing shape
(`{status, tool, tier_ceiling, external_id, fragment_id, action, tier}`,
[`creek_mcp/tools/journal.py`](../../creek-tools/creek_mcp/tools/journal.py))
minus `tool` — an MCP-vocabulary concept that the route itself already
identifies. `JournalUpsertResponse` is therefore
`{status, tier_ceiling, external_id, fragment_id, action, tier}`, with
`action ∈ {created, updated, unchanged}` (`JournalAction`).

**Always HTTP `200`, never `201`.** `action` already carries the
created-vs-not-created bit; duplicating it into the status line would put
that bit somewhere proxies, access logs and generic HTTP middleware
routinely inspect and normalize, which is exactly the layer this contract's
error taxonomy (below) is built to keep out of.

A request `tier` that is not expressible as one of the two `WireTierCeiling`
members (`open`, `personal` — `intimate` is not a constructible value; see
[INTIMATE](#intimate)) is `422 invalid_request`: a statement about the
caller's own malformed payload, which discloses nothing about the vault —
not `403`, which this contract reserves for a statement about a vault
object.

## Reflection

`POST /v1/reflections`.

The canonical result is **anchored margin notes plus an optional ungrounded
essay** — Creek's existing shape (`ReflectionResponse`) — and it may
**never** be collapsed to a bare string. `content` and `entry_ref` are
mutually exclusive and individually optional on the wire, but exactly one
must be supplied: both together, or neither, is `422`
(`ReflectionRequest._require_exactly_one_source`). `/v1` refuses to silently
prefer one over the other — unlike ambiguity elsewhere, an ambiguous request
that silently resolves is how the MCP and application surfaces would drift
from each other again, which is the failure mode the six-divergence table
below already reproduces once.

**`essay_grounded` is load-bearing.** It is required with no default, and
`True` is rejected at contract `0.2` — structurally, as
`ReflectionResponse.essay_grounded: Literal[False]`, so the constraint
reaches the *published* schema as a `const` rather than living only in the
running server. That distinction is the point: a runtime-only validator would
have left `schemas/ReflectionResponse.schema.json` saying `"type": "boolean"`,
and a consumer validating against the bundle this ADR publishes would have
accepted a payload the server rejects. No grounded-essay path exists yet,
`essay` is free model prose that is never verbatim-checked the way
`notes[].quote` is, and a client may never treat the essay as grounded.
Lifting this is a capability a consumer can detect, so it is a minor-version
event, not a silent relaxation.

Every `notes[].quote` is a server-verified verbatim (whitespace-normalized)
span of the entry: `reflect_tool`'s `_clean_notes` drops any note whose
`quote` does not pass `_is_verbatim` against the source entry before the
response is ever built
([`creek_mcp/tools/reflect.py`](../../creek-tools/creek_mcp/tools/reflect.py)).

**Care escalation is a `200`, not an error.** It arrives as
`CareEscalationResponse` — `status: "escalate"` plus a `reason` and the
structured `care_signal` (mirroring `creek.care.guardrail.CARE_SIGNAL`
whole, never abridged). A client that maps this to a failure path breaks the
care contract, which is exactly why `care_escalation` is deliberately **not**
a member of `ErrorCode`: a person in acute distress must not have their
response swallowed by generic error handling.

**`routed_tier` provenance — safe to expose, stated why.**
`routing_tier(ceiling, tier)` in
[`creek_mcp/tier_ceiling.py`](../../creek-tools/creek_mcp/tier_ceiling.py)
returns the more sensitive of `CEILING_ROUTING_TIER[ceiling]` and the
content's own (routing-normalized) tier. The above-ceiling admission gate
runs strictly before this call, so for every ceiling `/v1` permits (`open`,
`personal` — the remote cap) and every `PrivacyTier` that ceiling admits at
all, the *admitted* content's routing tier can never exceed
`CEILING_ROUTING_TIER[ceiling]` — which means `routed_tier` on the wire
equals a value derived only from the caller's own declared header, not from
anything about the resolved content. It is therefore a constant function of
information the caller already supplied, and publishing it discloses zero
additional bits. This is pinned by
`test_routed_tier_is_a_constant_function_of_the_declared_ceiling` in
`tests/test_adepthood_contract_models.py`. **If that test ever fails, the
field must be removed from `ReflectionResponse` — the test must never be
relaxed to accommodate a content-dependent value.**

## Wheel

`GET /v1/wheel` returns **Creek's own frequency counts and shares, verbatim**
— the corpus fact Creek actually owns, not a projection into anyone else's
vocabulary. `WheelFrequencies` declares all ten frequencies as separate
required fields, in the canonical `CANONICAL_FREQUENCY_NAMES` order, so the
published JSON Schema is `required: [F1 .. F10]` rather than an open
mapping. An empty (or all-`unclassified`) corpus yields an all-zero wheel and
is **not** an error (see the fifth capabilities state above). `share` sums
to `1.0 ± float error` when `total_classified > 0`; the contract does not
promise an exact `1.0`.

**Ownership split, stated explicitly.** The stage/aspect *projection* onto
Adepthood's own curriculum model is Adepthood's to own and test — tracked on
their side as `adepthood#1937`. **The F1–F10 ↔ ten-stage numeric coincidence
is not a semantic identity.** Creek's `share` is a fraction of the
*classified* corpus that sums to `1.0` across the ten frequencies; Adepthood's
per-stage `fullness` is curriculum completion in `[0, 1]` with no such
summing constraint — they are genuinely different quantities that happen to
both be ten numbers. `docs/decisions/2026-06-30-adepthood-creek-mcp-contract.md`
pins the shared vocabulary as the APTITUDE frequency axis and aligns
*frequencies / Aspects / Stages* **at the naming layer only**, carrying this
paragraph's hedge explicitly; it is Adepthood's own
`docs/creek-vault-mcp-contract.md` that currently asserts the wheel is "the
same shape as Adepthood's local `WheelBalanceResponse`" and that the two
vocabularies are "one vocabulary under three names" at the *numeric* layer.
**This ADR supersedes that specific claim.** Any stage/aspect projection
built on top of `WheelResponse` must key its interpretation on
`ontology_version`, never on the bare integer count or share, so a future
ontology revision cannot silently mis-project an old wheel through a new
curriculum mapping.

## Error and refusal taxonomy

`/v1` publishes a single closed enum of nine machine-readable codes
(`ErrorCode`), mapped to HTTP status by a total table (`ERROR_STATUS`).
Clients must never parse prose to decide behavior. Every error response is
exactly `ErrorEnvelope` — `{code, message, request_id}`, `extra="forbid"` —
and `message` is drawn from a constant table (`ERROR_MESSAGES`) that is
never interpolated with caller or vault data; no message contains a `{`,
which is itself a pinned property so no later refactor can turn a constant
into a format string.

| `code` | HTTP | Emitted when | Retry disposition |
|---|---|---|---|
| `unauthenticated` | 401 | No valid consumer credential accompanied the request | `terminal` |
| `invalid_request` | 422 | The request — body **or** declared header — does not satisfy the published contract, including a `tier` or `X-Creek-Tier-Ceiling` naming `intimate`/`all` | `terminal` |
| `incompatible_version` | 409 | The requested contract minor is not served here | `terminal` |
| `privacy_refused` | 403 | The single answer for every vault-object non-answer: above the ceiling, purged, orphaned, schema-invalid, or deleted out of band | `terminal` |
| `not_found` | 404 | A **routing** code only — no such endpoint or path on this server; never emitted for a vault object | `terminal` |
| `unsupported_capability` | 501 | A published capability this server does not implement | `terminal` |
| `unavailable` | 503 | The vault is absent or unreadable; a human must act | `retry_after_operator_action` |
| `temporarily_unavailable` | 503 | A transient condition; backoff will clear it | `retry_with_backoff` |
| `internal_error` | 500 | An unexpected server fault | `retry_with_backoff` |

**The oracle section is the most important part of this ADR.** Per
distinction, which codes are safe to expose and which must collapse:

**Safe to expose** — every one of these is derived from the caller's own
input or the server's own static configuration, never from resolved vault
content: `invalid_request` (the caller's own malformed payload),
`incompatible_version` (the caller's own declared header compared against a
published constant), `unauthenticated` (the caller's own credential),
`unsupported_capability` (the server's static route table),
`unavailable` (vault presence — which `/v1/capabilities` already discloses
to the same authenticated caller, so this code adds zero new bits),
`temporarily_unavailable`, `internal_error`.

**The fence that keeps three of those safe.** `unavailable`,
`temporarily_unavailable` and `internal_error` are admissible only as
**global** statements — about the vault, the service, or the process. None of
them may ever be emitted *per vault object*. The moment one is (say, an
unhandled exception while resolving one `external_id` surfacing as `500`
where a sibling id returns `403`), it becomes the same existence-and-rank
oracle in a different status class, and the collapse rule below is defeated
through a side door. A handler that cannot answer for a specific object
without disclosing why MUST return `403 privacy_refused`.

**Must collapse** — every non-answer about a *vault object*. `privacy_refused`
carries the single fixed
[`read_gate.GENERIC_ABOVE_CEILING_REASON`](../../creek-tools/creek_mcp/read_gate.py)
and covers both "above your declared ceiling" and "unresolvable" (purged,
orphaned, schema-invalid, or deleted out of band). It names no tier, no
fragment, and no path.

**`not_found` is re-scoped to a routing code, never a content code.** It is
emitted only when the requested path is not a route this server exposes.
[#846](https://github.com/Geoffe-Ga/Creek-Vault/issues/846),
[#970](https://github.com/Geoffe-Ga/Creek-Vault/issues/970),
[#972](https://github.com/Geoffe-Ga/Creek-Vault/issues/972) and
[#1090](https://github.com/Geoffe-Ga/Creek-Vault/issues/1090) — whose
reasoning is recorded in
[`creek_mcp/read_gate.py`](../../creek-tools/creek_mcp/read_gate.py) — spent
five issues collapsing exactly these distinctions across the MCP surface;
#1090's own standard is that a file that exists, a name that resolves to
nothing, and a symlink resolving off the vault must all be byte-identical
below the admitting ceiling. A `404` that a caller could distinguish from a
`403` over a vault object would hand back precisely the existence-and-rank
oracle those issues removed. This is a deliberate narrowing of the taxonomy
issue #1072's Problem section originally sketched. Until
[#1074](https://github.com/Geoffe-Ga/Creek-Vault/issues/1074) mounts the
handlers there is nothing to enforce this against; the structural guard that
keeps it from regressing once they exist — an AST sweep over every `NOT_FOUND`
construction site, checked against a pinned routing-layer allowlist — is
tracked in [#1098](https://github.com/Geoffe-Ga/Creek-Vault/issues/1098).

**`creek.reflect`'s two refusal reasons collapse at the `/v1` boundary.** At
the MCP layer `reflect_tool` keeps `"entry_ref not found"` distinct from
`"entry_ref tier exceeds ceiling"`, and its "ACCEPTED RESIDUAL RISK" block
records that this is a coarse existence-and-rank oracle tolerated because a
stdio caller is local and fragment ids are unguessable. **`/v1` is remote by
construction, so it does not inherit that tolerance.** Both reasons MUST be
rendered as a single `403 privacy_refused` carrying
`GENERIC_ABOVE_CEILING_REASON`. That is not merely a recommendation — it is
structural: `ErrorEnvelope.message` is drawn from `ERROR_MESSAGES` keyed on
`code` alone and the envelope is `extra="forbid"`, so there is no wire
position in which a second reason could travel. Preserving the distinction
would require minting a second `ErrorCode`, which the collapse rule above
forbids.

What `/v1` *does* inherit is the **timing** side-channel that reasoning
names: the not-found path parses every fragment file whereas the
above-ceiling path early-returns at the match, so response latency still
distinguishes the two even though the response bytes do not. That residual is
accepted here rather than resolved, and it is the only inherited one —
never a code, status or message distinction.

Error bodies may never echo journal content, credentials, or tier-unknown
vault text. Pydantic validation errors on the way out of `/v1` must be
rendered without `input`/`ctx`/`url` — precisely the fields a framework's
default `422` handler tends to echo verbatim, which is one of the four
reasons this ADR does not adopt FastAPI (see
[HTTP framework](#http-framework)).

**No `retryable` field on the wire, ever.** Retry policy is the static,
published `retry-policy.json` table — a pure function of `code` — so it
provably carries zero bits beyond the code itself. A per-response computed
boolean would invite a future refinement that varies *within* one code
("this particular privacy refusal happens to be retryable"), which is
exactly how an oracle returns through the back door.

## #1082 — the contract's answer

`creek classify`'s privacy pass is escalate-only, and every remote consumer
token is capped at `ceiling=personal` (`REMOTE_ADMITTED_CEILINGS` in
[`creek_mcp/policy.py`](../../creek-tools/creek_mcp/policy.py), moved out of
`creek_mcp/server.py` by [#1073](https://github.com/Geoffe-Ga/Creek-Vault/issues/1073)
so the cap is adapter-independent rather than bound to MCP middleware). So once a
journal fragment's persisted tier reaches `intimate`, a remote consumer can
**never send that `external_id` again — not even an unchanged, idempotent
re-sync**.

The gate's *location* matters, and is easy to state wrongly. It is
`_refuse_unadmitted_overwrite` in
[`creek_mcp/tools/journal.py`](../../creek-tools/creek_mcp/tools/journal.py),
called by `journal_ingest_tool` **before** `_stage_entry` and therefore before
`creek.ingest.pipeline.run_ingest` — and so before
`write_fragment_idempotent`'s `record.content_hash != new_hash` comparison is
ever reached. The gate is *not* inside `write_fragment_idempotent`, and it
structurally cannot be: that function lives in the `creek` package, which may
never import `creek_mcp` (#1032). Because the gate sits above the hash
comparison in call order, an unchanged re-send is refused identically to a
genuine rewrite.

> **Binding rule for #1075.** `/v1`'s journal handler MUST enter through
> `creek_mcp.tools.journal.journal_ingest_tool` and MUST NOT call
> `creek.ingest.pipeline.write_fragment_idempotent` (or `run_ingest`)
> directly. Wiring a route to the pipeline function would bypass the
> overwrite gate entirely and let a `ceiling=personal` remote consumer
> clobber an intimate-escalated fragment — reopening the #970 bug class that
> the thin-route rule ("parse → call the existing tool function → serialize")
> exists to prevent.

Adepthood is both a remote consumer and the primary journal producer, so its
continuous sync **will** hit this in production.

What the consumer receives: `403 privacy_refused` with the generic message,
and nothing else. How it distinguishes permanent from transient: **by the
code alone, via the static retry table.** `privacy_refused` maps to
`terminal` for that `(endpoint, identifier)` pair — stop retrying, mark the
local record blocked, surface to the human as "a local operator must re-sync
this entry," and **never infer a tier from the refusal**.
`temporarily_unavailable` maps to `retry_with_backoff`. That is the entire
distinction, and it needs no extra field to express.

**Honest residual.** Because the refusal is deliberately blurred, a
genuinely recoverable case — a fragment purged, leaving a dangling ledger
record (#1080) — is also treated as terminal by a strict client, and stays
stuck until a local stdio re-send or a ledger repair. **#1072 does not
implement a content-hash carve-out for the unchanged-resend case**;
[#1082](https://github.com/Geoffe-Ga/Creek-Vault/issues/1082) tracks whether
one should be built, as a future contract-minor change.

## Auth and consumer identity

`/v1` reuses the existing bearer-token registry —
[`creek_mcp.remote_auth.load_consumer_tokens`](../../creek-tools/creek_mcp/remote_auth.py)
/ `ConsumerTokenVerifier` — and the same ≥32-character floor,
`creek_mcp.token_policy.MIN_TOKEN_LEN`. `/v1` MUST NOT introduce a second
token registry or a second length floor: both would be a place for the two
surfaces to drift out of lock-step, which is exactly what this epic exists
to prevent.

The authenticated `client_id` **becomes** the audit `consumer`, mirroring
`_effective_consumer` — and **`/v1` MUST NOT accept a client-supplied
`consumer` field**, in body, query string, or header. This resolves a live
bug: Adepthood currently sends the literal string `"CREEK_MCP_CONSUMER"` — its
`CONSUMER_ID` constant is the name of the *environment variable*, not a
value — as a `consumer` parameter, which Creek's tools do not recognize and
which is meaningless as an identity regardless. Deriving `consumer` from the
authenticated token, unconditionally, removes the whole class of bug.

Transport posture matches `_require_transport_confidentiality`: loopback may
serve plaintext; a non-loopback bind without `--tls-cert`/`--tls-key`
refuses to start rather than starting partially. **Missing or invalid
credentials fail closed with no capability disclosure.** The `401` body is
`{code, message, request_id}` and nothing else — no versions, no
`capabilities`, no `vault` — with a `WWW-Authenticate: Bearer` header whose
realm names no vault. Operational note for Adepthood: the token TTL
(`CREEK_MCP_TOKEN_TTL_SECONDS`) does not revoke the underlying shared
secret — only rotating the configured token is a logout.

## INTIMATE

`/v1` refuses `intimate` and `all` ceilings at the same point in the request
lifecycle `_BoundedFastMCP.call_tool` already does for remote MCP calls
today: one edge check before routing, before any vault read is attempted.
This is modelled structurally rather than as a runtime branch —
`WireTierCeiling` has exactly two members (`open`, `personal`), so the
refusal is a type-level fact: there is no admissible value a producer or
consumer could put on the wire, in any request or response position, that
names `intimate`. The ceiling arrives as `X-Creek-Tier-Ceiling`, defaulting
to `open` when absent (fail closed); responses carry
`Vary: X-Creek-Tier-Ceiling` so an intermediary cache cannot serve one
caller's ceiling-filtered response to another.

**An inadmissible ceiling header is `422 invalid_request`, not `403
privacy_refused`** — the same answer this contract gives a body carrying
`tier: "intimate"` (see [Journal upsert](#journal-upsert)), and for the same
reason. The value came from the caller's own header and no vault object was
resolved, ranked, or even looked at, so `403`'s message —
`GENERIC_ABOVE_CEILING_REASON`, "resolved content exceeds the declared tier
ceiling" — would be simply false. That is the distinction
`creek_mcp/read_gate.py` records for `creek.redact.scan` (#972): the generic
reason asserts that resolved content was ranked, and a gate that ranked
nothing must not borrow it. `403 privacy_refused` stays reserved for
statements about a vault object.

Note that `/v1`'s wording therefore differs from remote MCP's, which returns
its own specific reason ("remote consumers may not request a ceiling above
`personal`…", `creek_mcp/server.py`). Both disclose nothing beyond the
caller's own declared ceiling; the two adapters agree on the *boundary*, not
on the string.

## HTTP framework

**Decided: Starlette, with OpenAPI generated from our own Pydantic models.
Not FastAPI.**

1. FastAPI would be a new direct dependency whose own Starlette pin range
   must stay compatible with the MCP SDK's Starlette pin
   (`creek-tools/uv.lock:3462`). A conflict there would break the
   load-bearing MCP transport in order to buy ergonomic convenience on the
   new one — an asymmetric trade this ADR declines.
2. The OpenAPI document is itself a published, pinned artifact. FastAPI's
   generated OpenAPI document is a function of FastAPI's own version, so a
   routine FastAPI upgrade would silently rewrite the published contract
   underneath a consumer that has pinned it. Generating from
   `model_json_schema()` on `CONTRACT_MODELS` makes the document a function
   of our models alone.
3. FastAPI's automatic `422` handler echoes the offending input by default —
   directly violating the no-content-echo invariant this contract's error
   taxonomy depends on. We would have to override it on every route anyway,
   which deletes the largest ergonomic reason to adopt the framework in the
   first place.
4. The route table is six endpoints. The convenience a full framework buys
   scales with route-table size and does not clear the bar here.

**Note for #1074**: Starlette must be **promoted to a declared direct
dependency** in that issue's work — it is transitive today only via the MCP
SDK. Importing it directly without declaring it in `pyproject.toml` is
exactly the kind of undeclared-dependency drift this epic exists to stop.

**Note also that #1072 itself required zero dependency changes.**
`model_json_schema()` and `model_validate` are pure Pydantic, already a
direct dependency of `creek-tools`.

## Serving: uvicorn's own logging and the readiness probe

Two decisions from the #1117 review, both about how `creek-tools-api`'s own
uvicorn process behaves rather than about the wire contract above.

**uvicorn's access log is suppressed, not filtered.**
[`build_uvicorn_config`](../../creek-tools/creek_mcp/httpapi/cli.py) passes
`access_log=False` rather than reaching for a `log_config` override or a
`logging.Filter` that trims the client address and concrete path back out of
uvicorn's own logger. That logger is on by default and
runs *alongside*
[`AccessLogMiddleware`](../../creek-tools/creek_mcp/httpapi/logging.py), not
instead of it, so a filter would be a *second* redaction rule loose in the
process — free to drift from the middleware's the next time either one is
touched without the other. Total suppression has no rule to drift: there is
exactly one access log left in the process, and it is the audited one
described in [`creek-tools/docs/api.md`](../../creek-tools/docs/api.md)'s
"Request logging" section.

**The `GET /v1/capabilities` readiness probe is hoisted off the event loop
as a whole, not seam-by-seam.**
[`_vault_is_usable`](../../creek-tools/creek_mcp/httpapi/capabilities.py) is
the single synchronous seam under `handle_capabilities`: every blocking
filesystem call the handshake makes — the config read and YAML parse, the
marker stat, and an audit append that takes a thread lock and an `fcntl`
exclusive lock across a full `fsync` — is reachable from that one function
and nowhere else. `handle_capabilities` therefore wraps `_vault_is_usable`
whole in `starlette.concurrency.run_in_threadpool` rather than hoisting each
syscall beneath it individually; a narrower hoist would still leave some of
those calls on the loop for no benefit and buy an extra context switch for
the privilege. Inline, this probe blocked the event loop entirely — stalling
every other in-flight request, including `GET /v1/health` and
`RequestTimeoutMiddleware`'s own cancel scope, on the one endpoint every
client calls first.

**Not fixed here.** `creek_mcp/server.py`'s `_serve_network` builds its own
`uvicorn.Config` for the MCP network transport and passes it no
`access_log=False` — the identical omission this ADR's uvicorn decision
above corrects for `creek-tools-api`, so uvicorn's default access logger is
live there too, writing the client address and request line for every
network MCP call. It is out of scope for #1117 and is tracked as follow-up
[#1125](https://github.com/Geoffe-Ga/Creek-Vault/issues/1125).

## The published fixture bundle

[`docs/contracts/adepthood-v1/`](../contracts/adepthood-v1/) is the source of
truth for the wire shapes in this repository:
`manifest.json`, `retry-policy.json`, one `schemas/*.schema.json` file per
`CONTRACT_MODELS` entry (thirty at contract `0.12.0`, unchanged since
`0.11.0` because #1292 moves no `/v1` shape — twenty-seven at
`0.10.0` — twenty-three at
`0.9.0` — eighteen at `0.8.0`, plus `RelatedPraxis` and `RelatedEddy` from #873
and the three `Drive*Response` models from #1527 — plus
`ClassificationRequest`/`ClassificationResponse` and `LinkRequest`/`LinkResponse`
from #1570 — plus `DriveAuthorizationRequest`, `DriveAuthorizationResponse` and
`DriveAuthorizationExchangeRequest` from #1568), and forty-nine
`examples/<capability>/<state>.json` fixtures (seven capabilities × seven
states). Everything in the directory except its own `README.md` is
**generated** by `build_bundle()`
([`creek_mcp/api/bundle.py`](../../creek-tools/creek_mcp/api/bundle.py)), and
`test_committed_bundle_equals_a_fresh_build` in
`tests/test_adepthood_contract_models.py` asserts the committed bytes are
byte-identical to a fresh build — so the bundle cannot silently rot away from
the models it documents. `manifest.json` carries `contract_version`,
`ontology_version`, and a per-file sha256.

**"Published" concretely means copy-and-pin, not a package.** Adepthood
vendors the directory into its own repository by copy and pins
`manifest.json`'s own sha256 in its CI; the recommended fetch is a
`raw.githubusercontent.com` URL pinned to a commit sha. A stale vendored
copy surfaces at runtime as `409 incompatible_version`, never as silence.

**Residual, stated plainly.** Nothing here mechanically stops Adepthood's
vendored copy from drifting between fetches; the only client-side
enforcement is its own manifest-hash check. Creek-side, CI enforces
bundle↔model agreement via the round-trip test above. Publishing the bundle
as a GitHub Release asset — alongside the existing rolling `knowledge-graph`
release — is the natural upgrade path and is **explicitly not done here**:
no subtree, no submodule, no package.

**The three `NotApplicableExample` cells.** Care escalation is structurally
unreachable for `capabilities`, `journal-upsert`, and `wheel`: the
acute-distress guard runs only inside `reflect_tool`. Fabricating a
care-escalation response for those three cells would publish a response
shape the server can never actually emit; omitting the cells would break the
matrix's rectangularity, and a hole in a matrix reads as "not documented
yet" rather than "cannot happen" — exactly the distinction a cross-repo
consumer needs to be able to draw. Each unreachable cell is filled with an
explicit, machine-checkable `NotApplicableExample` that states *why* it is
unreachable.

**Security invariants.** No fixture contains a real journal body, a
credential, or an `intimate`-tier success response. The `refusal` state
fixtures are the intimate examples for every capability, and every one of
them is a refusal — that is the entire point of publishing them.

### The OpenAPI document is deliberately not in the bundle (#1111, 2026-08-21)

`creek-tools-api --print-openapi` generates the document on demand. It is not
committed, it is not a bundle file, and `manifest.json` has no row for it.
**That is a decision, not an oversight**, and the reasoning is recorded here
rather than left in an issue:

- **Committing it is a consumer-visible contract event.** Every file in the
  bundle is emitted by `build_bundle()` and hashed into `manifest.json`, and
  the manifest is the artifact Adepthood pins. Adding `openapi.json` adds a
  manifest row and therefore rewrites the manifest's own bytes and hash,
  requiring a coordinated re-pin on the consumer side. A documentation change
  must not emit that event.
- **The gap it leaves is narrow.** `tests/test_v1_api_openapi.py` pins the
  generated document's schema content against the committed
  `schemas/<Model>.schema.json` files, pins that every `$ref` resolves, pins
  its `(path, method)` set against the routes actually mounted, and pins every
  documented status against the published closed set. What is unpinned is only
  the *file* an operator vendors after running the generator.
- **Determinism is not the reason.** `creek_mcp/httpapi/cli.py` prints
  `json.dumps(build_openapi(), indent=2, sort_keys=True)`, the same canonical
  form `bundle.py`'s `_serialise` uses. Committing it stays cheap whenever it
  is taken up; it is declined on contract-event grounds.
- **A middle option stays open at zero manifest cost.** Publishing
  `openapi.json` as a rolling GitHub Release asset — the upgrade path the
  bundle's own residual note already names — would let an operator diff a
  vendored copy without touching the pinned bundle.

**Revisit trigger, recorded here because the issue's own trigger has already
elapsed twice.** #1111 asked to decide "at the next contract minor"; minors
`0.8.0` (#1524), `0.9.0` (#1527/#873), `0.10.0` (#1570), `0.11.0` (#1568) and
`0.12.0` (#1292) have each re-published the bundle since it was filed. So the trigger lives in this document, which is consulted
at every bump: **at the next minor that re-publishes the bundle, either add
`openapi.json` to `build_bundle()` or restate this decision in that minor's
change-log row.** The operator-facing statement of the same decision is in
[`creek-tools/docs/api.md`](../../creek-tools/docs/api.md#openapi).

## What this ADR does NOT decide

Out of scope, and not implied by anything above:

- **Any individual route's implementation** — #1074 (framework wiring),
  #1075–#1077 (the four endpoints' handler code).
- **The transport-neutral policy extraction** referenced by #1073 (pulling
  shared gate logic out from under both adapters).
- **Bulk or asynchronous import** (#1023).
- **Per-entry classification** (#874).
- **Confidential compute, client-side encryption, attestation, or BYOK** —
  entirely [#757](https://github.com/Geoffe-Ga/Creek-Vault/issues/757)'s.

  the same tool functions; none of their logic changes here.
- **A GitHub-Release-asset publishing mechanism for the fixture bundle** —
  noted above as the natural next step, explicitly not built in #1072.
